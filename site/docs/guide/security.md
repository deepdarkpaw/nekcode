# 安全使用

请把模型生成的命令和代码当作**不可信**的东西对待。nek 以启动它的账户的权限读写文件、执行命令，并且**不会**在每次调用工具前征求同意。扩展、语言服务器和其他子进程也以同样的权限运行，除非有操作系统或虚拟化层面的边界限制它们。

文件内容、代码注释、项目指令、命令输出、模型回复都可能通过**提示词注入**影响模型的行为。项目信任只控制启动时加载哪些项目资源，并不能让这些内容或由此产生的操作变得安全。

真正的安全来自限制 nek 能访问的文件、凭据、进程和网络服务，这样即使某个操作是错的甚至是恶意的，影响也有限。盯着对话记录、使用项目信任、事后检查改动，都**不构成**安全边界。

## 选择运行方式

| 运行方式 | 受保护的范围 |
|---|---|
| 直接以当前操作系统用户运行 | 只有该用户本来就访问不到的东西。用一个专用账户可以缩小权限，但仍然共享操作系统和网络 |
| 整个 nek 在容器、虚拟机或沙箱里运行 | 你没有暴露给该环境的宿主机文件和进程。暴露进去的凭据和网络服务仍可被访问。通常是最实用的强隔离方式 |
| nek 在外面，只有内置工具在隔离环境里执行 | 通过这些工具执行的操作碰不到宿主机资源。但 nek 本身和其他扩展仍在边界之外，隔离范围更窄 |

工作目录只决定资源的发现位置和工具的默认路径，**不阻止**命令访问 nek 进程能访问的其他路径。

无论哪种方式，都只提供任务需要的文件和服务。尽量不要把凭据放进运行环境，或使用范围小、有效期短的凭据。命令不需要联网时限制网络访问。

具体的隔离方法和各自的局限见 [在隔离环境中运行](/guide/containerization)。

## 项目信任 {#project-trust}

项目信任决定 nek 是否加载工作目录提供的大部分设置和资源，防止一个目录在你同意之前悄悄加载可执行的扩展。

### 哪些资源需要信任

在当前工作目录发现以下任何一项时，nek 需要一个信任决定：

- `.nek/settings.json`
- `.nek/extensions`、`.nek/skills`、`.nek/prompts`、`.nek/themes`
- `.nek/SYSTEM.md`、`.nek/APPEND_SYSTEM.md`
- 当前目录或上级目录中的项目 `.agents/skills`

只有一个空的 `.nek` 目录（或只有 `.nek/plans/`）不需要信任。

信任后，nek 会加载：项目设置；`.nek` 下的扩展、Skills、提示词模板、主题和系统提示词文件；项目的 `mcp.json`、`nek.yaml`、`agents/`（自定义子代理）。拒绝信任则跳过这些资源。

### 信任不覆盖的东西

- **项目指令**：`AGENTS.override.md`、`AGENTS.md`、`CLAUDE.md` 无论是否信任都会加载（除非用 `--no-context-files` 关闭）。即使拒绝了信任，也请把目录里的指令当作不可信输入。
- **会话目录**：项目的 `sessionDir` 设置在决定信任之前就会被读取（用来定位会话），拒绝信任无法撤销这一次读取。
- **工具权限**：信任之后，启用的工具仍以 nek 进程的权限运行，信任不限制它们能做什么。

### 如何做出信任决定

命令行参数 `--approve`（`-a`）或 `--no-approve`（`-na`）优先。没有命令行参数时：

1. 用户级扩展和命令行加载的扩展可以处理 `project_trust` 事件，第一个给出“是”或“否”的扩展做决定；
2. 没有扩展决定时，查找当前目录或其上级目录保存过的决定，最近的那个生效；
3. 都没有时，按全局设置 `defaultProjectTrust`（默认 `"ask"`，即询问你）。

保存的决定以规范化的目录路径记录在：

```text
~/.nek/agent/trust.json
```

在 nek 里用 `/trust` 保存当前目录的信任决定，供以后的 nek 进程使用。

### 非交互模式

print、JSON、RPC 模式无法显示信任提示。没有命令行参数、扩展或已保存的决定时：

- `defaultProjectTrust: "always"`：加载受保护的项目资源；
- `defaultProjectTrust: "ask"` 或 `"never"`：跳过它们。

自动化运行需要明确决定时，用 `--approve` 或 `--no-approve`。

::: tip defaultProjectTrust 只能在用户级设置
`defaultProjectTrust` 只能写在 `~/.nek/agent/settings.json` 里，项目设置不能决定自己是否被信任。
:::

## 降低影响、方便恢复

以下做法不能替代隔离，但能减少暴露面、让出错后更容易恢复：

- 只给 nek 访问任务需要的文件和服务；
- 大改动之前做快照、备份，或先提交到版本控制；
- 加载扩展前先审查源码，扩展在 nek 进程内执行；
- 使用范围小、有效期短的凭据；
- 把结果用到其他系统之前，检查 diff 和生成的内容；
- 导出或分享会话前检查内容，里面可能有提示词、工具参数、命令输出、文件内容，以及对话中出现过的凭据。

## Plan 模式不是沙箱

Plan 模式只限制 `edit` 和 `write` 只能改 Markdown 文件，`bash` 等其他工具仍然可用。它是工作流程上的约束，不是安全边界。

## 报告安全问题

请按仓库的 [Security Policy](https://github.com/deepdarkpaw/nekcode/blob/nek/SECURITY.md) 报告，不要为安全敏感的问题开公开 issue。

以下情况通常不在安全边界之内，除非报告证明绕过了权限边界或获得了本地用户原本没有的访问：本地代理的预期行为、来自不可信内容的提示词注入、没有内置沙箱、用户自己安装的扩展或 Skills 的行为。
